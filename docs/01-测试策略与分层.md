# 01 · 测试策略与分层

> 面试问「你的测试是怎么分层的」，答这一页。

## 一、金字塔，但先说清楚边界

```
              ╱╲
             ╱ E2E ╲          少而关键：真人视角的主流程、跨页面、发版前回归
            ╱──────╲         本仓库 tests/e2e（Playwright，5 条自动化）
           ╱  接口契约 ╲       主力：状态码、字段、权限、边界、异常
          ╱────────────╲     本仓库 tests/api（node:test，7 条自动化）
         ╱   单元 / 组件  ╲    最快最多：纯函数、adapter、组件逻辑
        ╱──────────────────╲  留在 portfolio-cms 原来的 frontend/test + backend/test
```

**本仓库不重复造单测。** 被测项目里已经有 60+ 个 vitest / node:test 用例，
它们贴着源码跑、改一行就能验，归项目自己管。这个独立仓库只做**黑盒**：
把整个系统当一个盒子，从外面敲它、看它怎么响应。

这样分工的理由：单测回答「这个函数写对了吗」，黑盒测试回答
「前后端接起来之后，用户能不能把事办成」。两者不能互相替代。

## 二、两层各自的被测对象

| | 接口契约层 | 页面 E2E 层 |
| --- | --- | --- |
| 被测对象 | 真实 Express 后端 | 前端 demo 构建产物（自带假后端） |
| 启动方式 | `sut-server.mjs` 自动起，内存库 | `static-server.mjs` 自动起，本地复刻 Pages |
| 地址 | `http://127.0.0.1:3301` | `http://127.0.0.1:4173/portfolio-cms/` |
| 框架 | Node 内置 `node:test`，零依赖 | Playwright Test + 系统 Chrome |
| 关注 | 状态码 / 字段 / 权限 / 边界 / 错误体 | 元素可见 / 交互结果 / 地址栏 / 正文 |
| 速度 | ~3 秒 | ~32 秒 |

为什么 E2E 用 demo 构建产物（假后端）而不是真后端？
因为 E2E 要验的是**前端行为**：点击、滚动、路由、渲染。
把真后端的可用性混进来，一条用例就同时依赖两件事，失败时不知道怪谁。
真后端由接口层单独负责 —— 这是「失败要能定位」的设计。

## 三、环境策略：默认可离线，线上可选

| 场景 | 怎么做 |
| --- | --- |
| 日常 / `npm test` | 本地后端 + 本地静态站点，全自动起停，离线可跑 |
| 发版后抽查 | `E2E_BASE_URL=https://morris8088.github.io/portfolio-cms/ npm run test:e2e` |
| CI | 把被测仓库 checkout 到 `sut/`，构建后同样跑本地靶子 |

第一版默认打线上，结果两个 worker 并发就 `net::ERR_TIMED_OUT`：
**失败原因是网络，不是产品**。这种"假红"会让人逐渐不信任测试结果，
所以改成默认本地。外部地址保留为可选能力，而不是默认依赖。

## 四、数据隔离（这条最能体现专业度）

| 风险 | 处理 |
| --- | --- |
| 测试写脏开发数据库 | `DB_FILE=:memory:`，内存库，进程退出即消失 |
| 上传测试塞满 `uploads/` | `UPLOAD_DIR` 指向临时目录，退出时 `rmSync` |
| 端口占用 / 僵尸进程 | 用 3301 避开开发端口；`with-sut.mjs` 的 `finally` 保证一定关服务 |
| 用例之间互相污染 | 并行度设 1；`fixtures/factory.js` 每次造带随机后缀的新数据 |
| 测试依赖"数据库里恰好有第 3 篇" | 不断言具体条数，只断言「每一项都满足条件」 |

`with-sut.mjs` 里没有 `sleep(2000)` 这种猜时间的写法，
而是**轮询 `/api/health`**，服务真的能应答了才开跑。

## 五、稳定性设计小结

- 元素等待用 `expect(...).toBeVisible()` 自动重试，不用 `waitForTimeout` 硬睡
- 平滑滚动用 `expect.poll(...)` 反复确认，不假设动画 500ms 一定结束
- 失败才留截图和 trace（`screenshot: 'only-on-failure'`），平时不产生垃圾
- 两层都跑完才汇总，第一层挂了也要看到第二层的结果
- 报告永远生成，失败时更要看报告

## 六、准入 / 准出（说给面试官听的"标准"）

**准入**（什么样的改动要跑测试）：接口字段、路由、鉴权、前端首页/详情/路由任一改动。

**准出**（什么情况算可以发布）：
1. 接口层与页面层 0 失败；
2. P0 用例全部通过（清单里 `priority: P0`）；
3. 新增缺陷必须补一条对应的回归用例，见 `docs/03-缺陷清单.md`。

第 3 条是重点：修完 bug 不补回归 = 同一个坑迟早再踩一次。
这个项目的 4 个真实缺陷，每一个都在 `reader.spec.js` / `smoke.test.js` 里留下了对应断言。
