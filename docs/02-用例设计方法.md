# 02 · 用例设计方法

> 面试问「这些用例你是怎么想出来的」，答这一页。
> 只会写 `assert.equal(status, 200)` 不叫会测试；能说清**为什么测这条、不测那条**才叫会。

## 一、六种方法，配本项目实例

| 方法 | 意思 | 本项目的例子 |
| --- | --- | --- |
| 等价类划分 | 把输入分堆，每堆挑一个代表 | 登录：正确凭据 / 错误密码 / 不存在的账号 / 缺字段 |
| 边界值分析 | 专挑 0、1、上限、超大值 | `page=0`、`pageSize=0`、`pageSize=9999`、上传 6MB |
| 异常流 | 输入不合法时系统怎么收场 | 未知接口 404 且**必须是 JSON**；slug 重复 409；空更新 400 |
| 权限越权 | 换个身份还能不能拿到数据 | 游客列表不出现草稿；未登录 POST 返回 401 且没真的写入 |
| 契约校验 | 字段名、类型、结构就是合同 | `items` 是数组、`total` 是数字、`totalPages = ceil(total/pageSize)` |
| 回归 | 修过的 bug 必须钉死 | 点「读读文章」不换地址；直接访问 `#/posts` 不落 404 |

### 一个具体的边界值例子

`TC-API-006` 不是随手写的三个数：

- `page=0` —— 下界之外，验证「纠正为 1」而不是「报错」；
- `pageSize=0` —— 下界，验证「回落到默认 6」；
- `pageSize=9999` —— 上界之外，验证「夹到 50」，防的是有人一次把整库拉出来。

注意断言的是**被夹回合法范围**，不是「应该报错」。
公开接口对脏参数要宽容，这也是产品约定 —— 测试用例是在守护约定，不是在猜实现。

### 一个具体的安全例子

`TC-API-011` 要求「密码错误」和「账号不存在」返回**同一个状态码、同一句文案**。
如果文案不同（"密码错误" vs "用户不存在"），攻击者就能拿登录框当字典，
挨个试出哪些账号是注册过的。这叫**账号枚举漏洞**。
一条断言背后是一个真实的安全知识，面试讲这个比讲十个 200 有用。

`TC-API-034` 是另一个：把 `created_at;DROP TABLE posts;--` 塞进 `sort`，
不只断言返回 200，还**再查一次列表确认表和数据都还在**。
只断言"没报错"会把"注入已执行但恰好没当场崩"漏过去。

## 二、编号规则

```
TC-API-001   ↑ 层次(API/E2E)  ↑ 模块内序号
             010 登录 / 020 CRUD / 030 查询 / 040 上传
TC-E2E-001   001 读者主流程 / 010 后台
```

编号写进用例标题、`cases/testcases.json`、文档和报告，四处处处对得上。
缺陷清单里也用编号反查：「BUG-004 由 TC-E2E-002 守住」「BUG-005 由 TC-API-042 发现」。

## 三、单一数据源

`cases/testcases.json` 每条用例只写一次：

```json
{ "id": "TC-API-004", "layer": "api", "module": "权限",
  "title": "游客列表不出现草稿", "priority": "P0",
  "method": "权限越权", "status": "automated", "file": "tests/api/smoke.test.js" }
```

`scripts/make-report.mjs` 直接读它生成报告表格。
**不要**再手写一份 markdown 表格 —— 三份表格迟早对不上，
而"文档说 40 条、报告显示 37 条"在面试里是减分项。

`status` 目前 39 条全部是 `automated`；`practice` 的语义保留给将来新规划的用例。
文件顶层还有 `knownIssues`，用来登记「测试发现、但被测项目暂不修复」的风险，
报告会把它单独渲染成一块「遗留风险」。

**清单状态和运行结果不是一回事**：清单说"这条用例存在"，
报告里的「本次执行通过 39」来自 TAP 的 `# pass` 和 Playwright JSON 的 `stats.expected`。
两边分开，才能发现"清单标了 automated 但用例没跑起来"这类问题。

## 四、一条用例的标准形状

```js
test('TC-XXX-000 一句话说清验什么', async (t) => {
  // 1. 准备：自己造数据，并登记清理
  const token = await login();
  const ids = [];
  t.after(async () => { for (const id of ids) await api(`/api/posts/${id}`, { method: 'DELETE', token }); });

  // 2. 执行
  const { status, data } = await api('/api/posts');

  // 3. 断言（带上失败原因，出问题一眼看懂）
  assert.equal(status, 200);
  assert.ok(data.items.every(p => p.status === 'published'),
    '公开列表里混进了非 published 的文章');
});
```

准备 → 执行 → 断言，加上「用完自己删」这条纪律。
`assert` 不抛错就是通过，抛错就打印「期望值 vs 实际值」。

## 五、两个判断题（比多写十条用例值钱）

### 判断一：这个环境能验什么？

`TC-E2E-012` 原计划是「密码错误给出提示且停留登录页」。
但默认页面靶子是 Demo 构建，假后端 `mockAdapter.js` 的登录接口**接受任意账号密码**，
在这上面写「密码错误」只能得到一条假绿或一条永远红的用例。

处理方式是**把验证挪到能验的层次**：

- 页面层改测前端自己的必填校验（真实的前端行为，能测到）；
- 真实后端的「密码错 → 401 + 统一文案」由 `TC-API-011` 覆盖。

用例标题也跟着改了，并在 `admin.spec.js` 文件头写清原因。
**换测法不是妥协，是承认环境边界**；硬写一条永远红的用例才是失职。

### 判断二：发现了缺陷，要不要让它变红？

`TC-API-042` 跑的时候顺手探针了一下：把内容为 `<script>alert(1)</script>` 的文件
命名成 `looks-like-image.png` 上传，实测返回 **201** —— 后端只查扩展名，不嗅探内容。

要不要写 `assert.equal(status, 400)` 让它红？**不。**

- 测试红 = 有人需要立刻处理；但被测项目是另一个仓库，本工程的 CI 会一直挂着，
  几周后就没人看红了，这是「告警疲劳」。
- 更不能写 `assert.equal(status, 201)`：那等于宣布"这个 bug 是产品契约"，
  将来被测项目修好了，测试反而变红。

实际做法：用例里只 `console.log` 记录实测值，把证据、影响、修复建议、
以及「为什么不写成断言」写进 `cases/testcases.json` 的 `knownIssues` 和 `docs/03`，
报告渲染成可展开的「遗留风险」。等被测项目修好，再把探针改成 400 的验收断言。

**全绿 ≠ 没有缺陷。** 报告如实呈现「39 条通过 + 1 条遗留风险」，
比假装干干净净更可信。

## 六、四个坏味道（自己 review 时照着查）

1. **写死数据**：`assert.equal(data.total, 5)` —— 演示数据一变就红，用例很脆。
   改成 `data.items.every(...)` 这类「性质断言」。
2. **依赖执行顺序**：第二个用例用第一个用例创建的 id，单独跑就挂。
   用 `fixtures/factory.js` 自己造数据，用 `t.after()` 自己删。
3. **只数卡片不查错误**：页面渲染了空态也算"没报错"。
   要同时断言「有卡片」和「没有请求失败提示」，见 `TC-E2E-001`。
4. **用 sleep 等异步**：`waitForTimeout(2000)` 在慢机器上不够、在快机器上白等。
   用 `expect(...).toBeVisible()` / `expect.poll(...)`。

## 七、继续往下想

挑 `cases/testcases.json` 里任意一条，先**不写代码**，回答三个问题：

1. 这条用例防的是什么事故？
2. 如果它变红了，我第一步去看哪里？
3. 被测代码怎么改，会让它"该红却没红"？

第 3 问最容易被忽略 —— 它检验的是断言有没有真正覆盖风险，而不只是跑通流程。
