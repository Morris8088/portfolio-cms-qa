# 02 · 用例设计方法

> 面试问「这些用例你是怎么想出来的」，答这一页。
> 只会写 `assert.equal(status, 200)` 不叫会测试；能说清**为什么测这条、不测那条**才叫会。

## 一、六种方法，配本项目实例

| 方法 | 意思 | 本项目的例子 |
| --- | --- | --- |
| 等价类划分 | 把输入分堆，每堆挑一个代表 | 登录：正确凭据 / 错误密码 / 不存在的账号 / 缺字段 |
| 边界值分析 | 专挑 0、1、上限、超大值 | `page=0`、`pageSize=0`、`pageSize=9999`、上传 6MB |
| 异常流 | 输入不合法时系统怎么收场 | 未知接口 404 且**必须是 JSON**；请求体不是合法 JSON 返回 400 而非 500 |
| 权限越权 | 换个身份还能不能拿到数据 | 游客列表不出现草稿；未登录 POST 返回 401 且没真的写入 |
| 契约校验 | 字段名、类型、结构就是合同 | `items` 是数组、`total` 是数字、`totalPages = ceil(total/pageSize)` |
| 回归 | 修过的 bug 必须钉死 | 点「读读文章」不换地址；直接访问 `#/posts` 不落 404 |

### 一个具体的边界值例子

`TC-API-006` 不是随手写的三个数：

- `page=0` —— 下界之外，验证「纠正为 1」而不是「报错」；
- `pageSize=0` —— 下界，验证「回落到默认 6」；
- `pageSize=9999` —— 上界之外，验证「夹到 50」，防的是有人一次把整库拉出来。

注意断言的是**被夹回合法范围**，不是「应该报错」。
公开接口对脏参数要宽容，这也是产品约定 —— 测试用例是在守护约定，不是在猜实现。

### 一个具体的安全例子

`TC-API-011` 要求「密码错误」和「账号不存在」返回**同一个状态码、同一句文案**。
如果文案不同（"密码错误" vs "用户不存在"），攻击者就能拿登录框当字典，
挨个试出哪些账号是注册过的。这叫**账号枚举漏洞**。
一条断言背后是一个真实的安全知识，面试讲这个比讲十个 200 有用。

## 二、编号规则

```
TC-API-001   ↑ 层次(API/E2E)  ↑ 模块内序号
             010 登录 / 020 CRUD / 030 查询 / 040 上传
TC-E2E-001   001 读者主流程 / 010 后台
```

编号写进用例标题、`cases/testcases.json`、文档和报告，四处处处对得上。
缺陷清单里也用编号反查：「BUG-004 由 TC-E2E-002 守住」。

## 三、单一数据源

`cases/testcases.json` 每条用例只写一次：

```json
{ "id": "TC-API-004", "layer": "api", "module": "权限",
  "title": "游客列表不出现草稿", "priority": "P0",
  "method": "权限越权", "status": "automated", "file": "tests/api/smoke.test.js" }
```

`scripts/make-report.mjs` 直接读它生成报告表格。
**不要**再手写一份 markdown 表格 —— 三份表格迟早对不上，
而"文档说 40 条、报告显示 37 条"在面试里是减分项。

`status` 两个值：`automated`（已实现）、`practice`（练习位）。
练习位会如实显示为待办，不伪装成通过。

## 四、一条用例的标准形状

```js
test('TC-XXX-000 一句话说清验什么', async () => {
  // 1. 准备 + 执行
  const { status, data } = await api('/api/posts');

  // 2. 断言（带上失败原因，出问题一眼看懂）
  assert.equal(status, 200);
  assert.ok(data.items.every(p => p.status === 'published'),
    '公开列表里混进了非 published 的文章');
});
```

三段：准备 → 执行 → 断言。没有第四段。
`assert` 不抛错就是通过，抛错就打印「期望值 vs 实际值」。

## 五、四个坏味道（自己 review 时照着查）

1. **写死数据**：`assert.equal(data.total, 5)` —— 演示数据一变就红，用例很脆。
   改成 `data.items.every(...)` 这类「性质断言」。
2. **依赖执行顺序**：第二个用例用第一个用例创建的 id，单独跑就挂。
   用 `fixtures/factory.js` 自己造数据，用完自己删。
3. **只数卡片不查错误**：页面渲染了空态也算"没报错"。
   要同时断言「有卡片」和「没有请求失败提示」，见 `TC-E2E-001`。
4. **用 sleep 等异步**：`waitForTimeout(2000)` 在慢机器上不够、在快机器上白等。
   用 `expect(...).toBeVisible()` / `expect.poll(...)`。

## 六、给你的小练习

打开 `cases/testcases.json`，挑一个 `practice` 用例，
先**不写代码**，用一句话回答：「这条用例防的是什么事故？」
答得出来再动手写断言 —— 这个习惯比多写十条用例值钱。
