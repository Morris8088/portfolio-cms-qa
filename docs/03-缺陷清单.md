## BUG-001 · 假后端路径匹配，全站接口失败

**现象**：线上 Demo 首页文章区空白，用户报「没文章是什么情况」。

**根因**：`mockAdapter.js` 在拿路径去做正则匹配前，先做了「去掉开头斜杠」的归一化，
而路由表里登记的却是带 `/` 的写法。结果**每一个接口都匹配不上**，
文章、标签、作品集全部拿不到数据。

**为什么当时没被测出来**：原有单测只验了 adapter 的内部匹配逻辑，
没有一条用例从"首页打开后到底有没有卡片"这个结果视角看问题。
**单元全绿 ≠ 系统能用**。

**修法**：抽出 `normalizePath()` + `findRoute()` 统一路径口径，补 14 条回归测试。

**现在的守门用例**：`TC-E2E-001` 正面断言"未登录读者能看到卡片"，
并同时断言页面里没有「请求失败」字样 —— 空态和请求挂了是两回事，不能只数卡片。

## BUG-002 · 假后端装得太晚，第一个请求打空

**现象**：首页「共 0 篇 + 请求失败（404）」，点文章进 404 页，但后台列表明明有 5 篇。

**根因**：`api/index.js` 写的是 `import('../demo').then(m => m.installDemoMode(request))` ——
发起动态加载，**但没人等它**。`main.js` 紧接着 `app.mount()`，
首页 `onMounted` 立刻发 `/posts`；此时假 adapter 还没装上，
请求真的打向 `/api/posts`，而 GitHub Pages 上没有这个文件 → 404。
晚几百毫秒发出的 `/tags`、`/projects` 反而正常，所以看起来像"只有文章坏了"。

**为什么当时没被测出来**：这是**时序问题**。单元测试能验"装好之后逻辑对不对"，
验不了"什么时候装好"。凡是「异步准备 → 同步使用」的顺序，必须用真浏览器跑一遍。

**修法**：`api/index.js` 导出 `demoReady` Promise，`main.js` 在 `app.mount()` 之前 `await demoReady`。

**现在的守门用例**：`TC-E2E-001`（首页有卡片且无请求失败）、`TC-E2E-003`（详情页正文长度 > 50）。
后者专门防"标题渲染了、正文没拿到"这种半吊子成功。

## BUG-003 · SPA 兜底把深链送错地方

**现象**：直接访问不带 `#` 的文章地址落在 404 页。

**根因**：`public/404.html` 负责把 `/posts/2` 这种路径转成 `/#/posts/2`，
但仓库前缀是按 `location.hostname` 推断的，在某些环境里推成了 `/`，
拼出来的地址少了 `/portfolio-cms/`，自然 404。
（这条是排查 BUG-002 时顺带发现并修掉的，不是用户单独报的。）

**修法**：前缀改为显式写死仓库名；CI 增加「构建后校验 dist 产物」步骤，
避免残缺的 dist 被当成部署成功。

**现在的守门用例**：`TC-E2E-004`（`#/posts` 被接住）、`TC-E2E-005`（深链 `#/posts/2` 正文完整）。

## BUG-004 · hash 路由下，`#` 不是页面锚点

**现象**：后台 5 篇「已发布」看得见，点首页「读读文章」→ 地址变成 `#/posts`
→ 「这个地址没有内容」。用户当时的原话是：
「只有自己发布者看得见，读者看不见有啥用啊」。

**根因**：`Home.vue` 写的是 `href` 指向 `#posts` 的普通 `<a>` 标签，
本意是滚到本页下方的 `<section id="posts">`。
但这个 Demo 用 **hash 路由**，地址栏 `#` 后面整段都归 Vue Router 管，
`#posts` 被规范化成 `/posts`；路由表只有 `/posts/:id`（具体某篇），
没有 `/posts` —— 于是落进兜底 404 页。

**文章数据一直都在首页下方，没丢，也没有做任何登录隔离。**
这是个"看起来像权限问题、其实是路由问题"的典型误诊。

**为什么当时没被测出来**：原有 e2e 只走了"点卡片进详情"，
没走"点顶部按钮"这条路径。用例覆盖的是**开发者以为用户会走的路**，
不是用户实际走的路。

**修法**：按钮改成 `<button>` + `scrollIntoView`（只动滚动条、不动地址栏）；
router 加 `/posts` → 首页文章区的 redirect，接住旧链接和分享地址。

**现在的守门用例**：`TC-E2E-002` —— 点之前记下 `page.url()`，
点之后断言**地址栏一个字都没变**、不出现 404 文案、且真的滚到了 `#posts`。
这三条缺一不可：只断言"没 404"会漏掉"偷偷换了路由但恰好有页面"的情况。

## BUG-005 · 上传只校验扩展名，未校验内容（新发现，未修复）

**发现方式**：补齐 `TC-API-042`（拒绝危险扩展名）时，顺手加了一个探针：
把内容为 `<script>alert(1)</script>` 的文件命名为 `looks-like-image.png` 上传。
实测 **HTTP 201，文件落盘**，控制台输出：

```
[已知风险 BUG-005] 伪装成 .png 的脚本上传返回 HTTP 201；
当前只校验扩展名，未校验文件内容，详见 docs/03-缺陷清单.md
```

**根因**：`routes/uploads.js` 的 `fileFilter` 只用 `extname(originalname)` 查白名单，
`ALLOWED` 里确实有 `.png`，所以放行；没有任何 magic number / 文件头校验。
作者当初的设计注释写的是「只信扩展名 + 白名单」，属于**刻意的范围取舍**，不是手误。

**为什么原来没被测出来**：被测项目自己的 `api.test.js` 里那条
「拒绝伪装成图片的可执行文件」用的文件名是 `payload.sh` —— 扩展名就不在白名单里，
测到的其实还是"扩展名过滤"，没有真正碰内容。

**影响**：白名单不含 `.html`，且上传目录是静态托管，直接执行脚本的路径有限；
但 `.svg` 在白名单里，SVG 可以内嵌脚本，若被当作图片直接打开就有存储型 XSS 风险。
属于**中风险、需要修但不用连夜修**。

**建议修法**：读取文件头校验真实类型（PNG `89 50 4E 47`、JPEG `FF D8 FF`、GIF、WebP），
不匹配就 400；给 `/uploads` 响应加 `X-Content-Type-Options: nosniff` 与 CSP；
对 `.svg` 单独做 XML 清洗或直接移出白名单。

**为什么没写成失败断言**：见 `docs/02` 第五节的判断二。
写成 400 会让独立测试仓库的 CI 长期挂红（告警疲劳），
写成 201 等于把 bug 固化成契约（将来修好反而变红）。
所以只记录实测值 + 影响 + 建议，登记进 `cases/testcases.json` 的 `knownIssues`，
报告里渲染成可展开的「遗留风险」。等被测项目修好，这一步探针就能直接改成验收断言。

## 这 5 条暴露的共同盲区

1. **只测零件，不测装配**：adapter 单测全绿，系统照样起不来。
2. **不测时序**：「异步准备 → 同步使用」的顺序问题，单测天然看不见。
3. **不测用户真实路径**：按钮就在首页最显眼处，却没人点过它。
4. **修完不补回归**：前三个 bug 是接连被用户报出来的，
   每次都只修当下、没把整类问题钉死，于是同一个"线上看不到文章"反复换个马甲出现。
5. **用例名字骗了自己**：「拒绝伪装文件」测的其实是 `payload.sh` 的扩展名，
   看起来覆盖了内容校验，实际一步都没走到。写用例时要问一句：**这条断言真的碰到了我说的那个风险吗？**

**所以这个独立测试工程的第一批自动化用例，全部是前 4 个事故的回归用例。**
不是为了凑数量，是为了让同一个坑不再踩第五次。
第 5 条则是补齐覆盖后才暴露出来的 —— 这本身就说明「把用例写完」是有价值的。
