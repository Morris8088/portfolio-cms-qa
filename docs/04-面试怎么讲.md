# 04 · 面试怎么讲（三个岗位，三套讲法）

> 同一个仓库，投不同岗位时**开场 30 秒就不一样**。
> 别一上来背目录结构，先说对方最关心的那件事。

## 通用开场（30 秒）

> 「我的主项目是一个 Vue 3 + Express + SQLite 的作品集 CMS。
> 上线之后连续出了 4 个『用户看得到、开发自测没发现』的线上缺陷，
> 所以我单独拆了一个测试仓库，把这几个事故全部固化成回归用例，
> 再补上用例设计、CI 和可视化报告。现在 `npm test` 一条命令跑两层、出一份报告。」

**诚实提示**：目前 12 条已自动化、27 条是留给我自己补的练习位。
被问到数量就说「12 条跑通、清单里规划了 39 条，练习位在 `test.todo` 里明确标着」，
**不要说 39 条全部自动化** —— 面试官一翻代码就穿帮，反倒不如坦白加分。

---

## 投「测试」岗

**主线：我不是只会写 assert，我懂设计和流程。**

讲这四点，按顺序：

1. **用例怎么来的** → `docs/02`。等价类、边界值、异常流、权限越权、契约、回归六类，
   每类举一个本项目实例。重点讲 `TC-API-011`（防账号枚举）和 `TC-API-006`（三个边界值）。
2. **缺陷闭环** → `docs/03`。4 个真实线上缺陷，每个都对应一条回归用例；
   强调「修完不补回归 = 同一个坑再踩一次」，这 4 个 bug 正是接连被报出来的。
3. **环境隔离** → `docs/01` 第四节。内存库、临时上传目录、自动起停、
   轮询健康检查而不是 sleep、并行度 1 防用例互污。
4. **报告与 CI** → `reports/index.html` 单一数据源、失败留截图/trace、
   `.github/workflows/qa.yml` 自动拉被测项目构建并上传报告。

**高频追问**

- *「怎么保证测试不污染数据？」* → `:memory:` 内存库 + `UPLOAD_DIR` 临时目录 + 退出即删；
  用例自己造数据（`factory.js` 带随机后缀）、自己清理，不依赖数据库里"恰好有第 3 条"。
- *「用例失败了你怎么定位？」* → 先看是断言失败还是环境失败；
  本地靶子排除了外网因素，Playwright 失败自动留截图和 trace 可回放。
- *「为什么不做性能测试 / 覆盖率？」* → 目前优先级放在功能回归闭环；
  `client.js` 已经把每次请求耗时 `ms` 带回来了，`TC-API-001` 有一条健康检查 < 1s 的性能冒烟，
  后面可以基于同一份数据扩成基线对比。**不要硬编不会的东西。**

## 投「前端」岗

**主线：我懂浏览器里到底发生了什么，尤其是路由。**

讲这三点：

1. **hash 路由的坑** → BUG-004。`#` 后面是路由不是锚点，
   `<a href="#posts">` 会被规范化成 `/posts` 然后掉 404。
   正确做法是 `scrollIntoView` 只动滚动条；再配 router redirect 接住旧链接。
   这条能顺带聊 SPA 部署在子路径下、GitHub Pages 的 `404.html` 兜底原理。
2. **Playwright 实战** → `reader.spec.js`。
   `page.goto('./')` 而不是 `'/'`（子路径会丢前缀）、
   `expect(...).toBeVisible()` 自动等而不是 `waitForTimeout` 硬睡、
   `expect.poll` 等平滑滚动、失败才留证据。
3. **稳定性判断** → 为什么把默认靶子从线上改成 `static-server.mjs` 本地复刻 Pages。
   前端工程师能分清「产品 bug」和「环境抖动」，这点很加分。

**高频追问**

- *「为什么用系统 Chrome 不下载 Playwright 浏览器？」* → 少一个失败点、少 100MB 下载；
  `CHROME_PATH` 可覆盖，配置里三级回退。
- *「E2E 为什么用假后端？」* → 这一层只验前端行为（点击/路由/渲染）；
  真后端由接口层单独验，避免一条用例依赖两件事、失败时不知道怪谁。

## 投「后端」岗

**主线：接口是合同，鉴权与边界是底线。**

讲这三点：

1. **契约测试** → `smoke.test.js`。状态码、字段名、类型、错误体格式都是前后端合同；
   `TC-API-002` 专门断言「404 也必须是 JSON」，否则前端解析会崩成白屏。
2. **安全与越权** → `TC-API-004`（游客不见草稿）、`TC-API-005`（未登录写入 401
   且**复查没有真的写进去**）、`TC-API-034`（非法 sort 不能 SQL 注入）、
   上传的扩展名/大小/伪装文件（练习位 `TC-API-040~045`）。
3. **零依赖基建** → `node:test` + `fetch`，不装 jest/supertest；
   `app.js` 与 `index.js` 分离（组装 vs 启动），所以测试能 `listen(0)` / 指定端口，
   不会抢占开发端口。这个设计可以自然聊到依赖注入与可测试性。

**高频追问**

- *「你的测试和项目里 backend/test 有什么区别？」* → 那边是贴着源码的白盒/集成测试，
  这里是纯黑盒、只通过 HTTP 契约交互，换语言重写后端也不用改用例。
- *「分页的边界怎么处理？」* → `page=0` 纠正为 1、`pageSize=0` 回落默认 6、
  上限夹到 50 防止一次拉爆库；`TC-API-006` 把这三条钉死。

## 三条别踩的坑

1. **别吹全自动化**。练习位如实说是练习位，反而显得你清楚自己做到哪一步。
2. **别把"网络超时"说成"发现了一个 bug"**。第一版线上 E2E 超时是环境问题，
   我在文档里明确写了这是假红、并因此改成本地靶子 —— 这种判断力本身就是答案。
3. **别只讲工具名**。被问「为什么用 Playwright」时，
   答「因为能自动等待、失败留 trace、能复用系统 Chrome」，比答「因为主流」强得多。

## 演示顺序（现场如果让你打开电脑）

```
1. 打开 reports/index.html           → 先给结论：两层全绿、12 条自动化
2. 打开 docs/03-缺陷清单.md          → 讲故事：这 4 个事故怎么来的
3. 打开 tests/e2e/reader.spec.js     → 看回归用例怎么钉死它
4. 跑一次 npm test                   → 现场复现，约 35 秒
5. 打开 cases/testcases.json         → 讲单一数据源和 27 条练习位规划
```
