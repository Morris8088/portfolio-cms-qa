# 04 · 面试怎么讲（三个岗位，三套讲法）

> 同一个仓库，投不同岗位时**开场 30 秒就不一样**。
> 别一上来背目录结构，先说对方最关心的那件事。

## 通用开场（30 秒）

> 「我的主项目是一个 Vue 3 + Express + SQLite 的作品集 CMS。
> 上线之后连续出了 4 个『用户看得到、开发自测没发现』的线上缺陷，
> 所以我单独拆了一个黑盒测试仓库，把这几个事故固化成回归用例，
> 再补齐接口契约、页面流程、用例设计、CI 和可视化报告。
> 现在 `npm test` 一条命令跑 39 条：接口 30、页面 9，约 25 秒出报告。」

**诚实提示（现在可以大方说数字了）**：39 条**全部已自动化**，0 TODO、0 跳过、0 失败。
但别顺口说成"项目没有缺陷" —— 跑这套用例还发现 1 个被测项目**尚未修复**的风险
（BUG-005，上传不校验文件内容），报告里单列了「遗留风险」。
**「39 条全绿 + 1 条已知未修风险」这个说法，比"全绿"更专业，也经得起追问。**

还有一条更现实的提醒：数量不是重点，**你能讲清楚几行为什么这么断言**才是重点。
挑 5~8 条自己真正吃透的（`TC-E2E-002`、`TC-API-011`、`TC-API-024`、`TC-API-034`、
`TC-E2E-013` 这些最有故事），翻着代码讲。被追问细节答不上来，比少说 20 条更伤。

## 投「测试」岗

**主线：我不是只会写 assert，我懂设计和流程。**

讲这四点，按顺序：

1. **用例怎么来的** → `docs/02`。等价类、边界值、异常流、权限越权、契约、回归六类，
   每类举一个本项目实例。重点讲 `TC-API-011`（防账号枚举）、`TC-API-006`（三个边界值）、
   `TC-API-034`（注入之后要再查一次表还在）。
2. **缺陷闭环** → `docs/03`。4 个真实线上缺陷，每个都对应一条回归用例；
   强调「修完不补回归 = 同一个坑再踩一次」，这 4 个 bug 正是接连被报出来的。
   再主动讲第 5 个：`BUG-005` 是补完用例才发现的，被测项目还没修，
   我把它登记成已知风险而不是让 CI 变红，理由见 `docs/02` 第五节。
3. **环境隔离** → `docs/01` 第四节。内存库、临时上传目录、自动起停、
   轮询健康检查而不是 sleep、并行度 1 防用例互污、`t.after()` 兜底清理。
4. **报告与 CI** → `reports/index.html` 单一数据源、通过数来自 TAP/JSON 而非手填、
   失败留截图/trace、`.github/workflows/qa.yml` 自动拉被测项目构建并上传报告。

**高频追问**

- *「怎么保证测试不污染数据？」* → `:memory:` 内存库 + `UPLOAD_DIR` 临时目录 + 退出即删；
  用例自己造数据（`factory.js` 带随机后缀）、`t.after()` 自己清理；
  `TC-API-004` 排在 CRUD 之后，本身就是一道污染检测。
- *「用例失败了你怎么定位？」* → 先看是断言失败还是环境失败；
  本地靶子排除了外网因素，Playwright 失败自动留截图和 trace 可回放。
- *「39 条全绿，为什么还有缺陷？」* → 全绿只说明这 39 条断言描述的行为符合预期。
  BUG-005 在断言覆盖之外，是被测项目的范围取舍。发现它之后我选择记录证据和影响，
  而不是把它写成 201 的"期望值"—— 那样将来修好了测试反而会红。
- *「为什么不做性能测试 / 覆盖率？」* → 目前优先级放在功能回归闭环；
  `client.js` 已经把每次请求耗时 `ms` 带回来了，`TC-API-001` 有一条健康检查 < 1s 的性能冒烟，
  后面可以基于同一份数据扩成基线对比。**不要硬编不会的东西。**

## 投「前端」岗

**主线：我懂浏览器里到底发生了什么，尤其是路由。**

讲这三点：

1. **hash 路由的坑** → BUG-004。`#` 后面是路由不是锚点，
   `<a href="#posts">` 会被规范化成 `/posts` 然后掉 404。
   正确做法是 `scrollIntoView` 只动滚动条；再配 router redirect 接住旧链接。
   这条能顺带聊 SPA 部署在子路径下、GitHub Pages 的 `404.html` 兜底原理。
2. **Playwright 实战** → `reader.spec.js` + `admin.spec.js`。
   `page.goto('./')` 而不是 `'/'`（子路径会丢前缀）、
   `expect(...).toBeVisible()` 自动等而不是 `waitForTimeout` 硬睡、
   `expect.poll` 等平滑滚动、失败才留证据。
   `TC-E2E-013` 是完整跨角色链路：登录 → 写文章 → 发布 → 退出 → 刷新 → 读者看得到，
   最后那次 `page.goto('./')` 是刻意的，用来证明数据真的持久化了，不是组件内存里残留。
3. **稳定性判断** → 为什么把默认靶子从线上改成 `static-server.mjs` 本地复刻 Pages。
   前端工程师能分清「产品 bug」和「环境抖动」，这点很加分。

**高频追问**

- *「为什么用系统 Chrome 不下载 Playwright 浏览器？」* → 少一个失败点、少 100MB 下载；
  `CHROME_PATH` 可覆盖，配置里三级回退。
- *「E2E 为什么用假后端？」* → 这一层只验前端行为（点击/路由/渲染）；
  真后端由接口层单独验，避免一条用例依赖两件事、失败时不知道怪谁。
  代价是假后端不校验密码，所以「密码错误」挪到接口层测 —— 见 `TC-E2E-012` 的说明。
- *「登录态怎么保持/清除的？」* → Pinia store + localStorage 里的 token；
  退出只清 token 与用户信息，不清文章数据，`TC-E2E-013` 就是验这件事。

## 投「后端」岗

**主线：接口是合同，鉴权与边界是底线。**

讲这三点：

1. **契约测试** → `smoke.test.js`。状态码、字段名、类型、错误体格式都是前后端合同；
   `TC-API-002` 专门断言「404 也必须是 JSON」，否则前端解析会崩成白屏。
   `TC-API-020` 验后端自动补 slug / summary / 默认草稿，这些"隐式默认值"最容易在重构里丢。
2. **安全与越权** → `TC-API-004`（游客不见草稿）、`TC-API-005`（未登录写入 401
   且**复查没有真的写进去**）、`TC-API-024`（详情 / 公开列表 / 后台列表三层可见性）、
   `TC-API-034`（非法 sort 不能 SQL 注入）、
   上传组 `TC-API-040~045`（401、UUID 文件名、字节一致、白名单、413、重名、空请求）。
   顺带讲 `BUG-005`：这组用例跑出了一个未修风险 —— 只查扩展名不查文件内容，
   建议加 magic number 校验和 `nosniff`。
3. **零依赖基建** → `node:test` + `fetch`，不装 jest/supertest；
   `app.js` 与 `index.js` 分离（组装 vs 启动），所以测试能指定端口启动，
   不会抢占开发端口。这个设计可以自然聊到依赖注入与可测试性。

**高频追问**

- *「你的测试和项目里 backend/test 有什么区别？」* → 那边是贴着源码的白盒/集成测试，
  这里是纯黑盒、只通过 HTTP 契约交互，换语言重写后端也不用改用例。
- *「分页的边界怎么处理？」* → `page=0` 纠正为 1、`pageSize=0` 回落默认 6、
  上限夹到 50 防止一次拉爆库；`TC-API-006` 把这三条钉死，`TC-API-035` 再验分页不重复、越界不报错。
- *「409 是怎么产生的？」* → slug 上的 UNIQUE 索引，后端捕获 `UNIQUE` 异常翻译成 409；
  `TC-API-022` 同时断言"第二条没有落库"，而不只是看状态码。

## 三条别踩的坑

1. **别把「全部通过」说成「没有缺陷」**。39 条全绿是事实，
   1 条已知未修风险也是事实，两个一起说，才显得你清楚测试覆盖的边界。
2. **别把"网络超时"说成"发现了一个 bug"**。第一版线上 E2E 超时是环境问题，
   我在文档里明确写了这是假红、并因此改成本地靶子 —— 这种判断力本身就是答案。
3. **别只讲工具名**。被问「为什么用 Playwright」时，
   答「因为能自动等待、失败留 trace、能复用系统 Chrome」，比答「因为主流」强得多。

## 演示顺序（现场如果让你打开电脑）

```
1. 打开 reports/index.html           → 先给结论：39 条通过 + 1 条遗留风险（可展开）
2. 打开 docs/03-缺陷清单.md          → 讲故事：4 个线上事故 + 1 个新发现
3. 打开 tests/e2e/reader.spec.js     → 看回归用例怎么钉死 BUG-004
4. 打开 tests/api/uploads.test.js    → 看 BUG-005 探针为什么不写成断言
5. 跑一次 npm test                   → 现场复现，约 25 秒
6. 打开 cases/testcases.json         → 讲单一数据源、P0 优先级、knownIssues
```
